## Why this matters

`scripts/color-ramps.mjs` already computes every ramp step **in OKLCH**
(`rgbToOklch`/`oklchToRgb`, lines 70-92) — the primitives are OKLCH-native
today. What it does *not* do is emit OKLCH to the browser: `toHex` (lines
97-110) gamut-clips every color to sRGB (binary-searching chroma until the
result fits in `[0,1]` sRGB, lines 101-107) and writes only a hex string to
`palette.css`. That sRGB clip is throwing away color the two most saturated
ramps (`gold`, `red`) actually have in OKLCH — on a Display P3 screen (most
Apple hardware since 2016, most higher-end Android/Windows displays since
~2020), those colors could render more saturated than the clipped sRGB hex
allows. `oklch()` as a CSS value has broad browser support in 2026 (Chrome
111+, Safari 15.4+, Firefox 113+), so shipping it is not a compatibility risk
for a small business site with no stated legacy-browser requirement. This
plan adds a P3-gamut-mapped `oklch()` declaration for every ramp value,
written *after* the existing sRGB hex declaration for the same custom
property — a browser that doesn't understand `oklch()` silently keeps the
earlier hex value (CSS drops an unparseable declaration rather than falling
back to it or erroring), so this is a strict progressive enhancement, not a
replacement.

**What this plan deliberately does not change**: `palette.generated.json`
keeps its existing sRGB-hex-only shape, completely untouched by this plan.
`scripts/contrast.mjs` (WCAG math) and `scripts/figma-manifest.mjs` (Figma
variable sync) both read `palette.generated.json`, not `palette.css`, so
neither is affected — Figma variables and the WCAG contrast guarantees stay
exactly as precise and exactly as they are today. Only `palette.css`, the
file actual browsers load, gains the wider-gamut option.

## Current state

`scripts/color-ramps.mjs`, the relevant functions (full current text):

```js
const inGamut = (rgb) => rgb.every((v) => v >= -0.0005 && v <= 1.0005);

// Reduce chroma until the color fits in sRGB.
function toHex({ L, C, h }) {
  let lo = 0;
  let hi = C;
  let rgb = oklchToRgb({ L, C, h });
  if (!inGamut(rgb)) {
    for (let i = 0; i < 30; i++) {
      const mid = (lo + hi) / 2;
      if (inGamut(oklchToRgb({ L, C: mid, h }))) lo = mid;
      else hi = mid;
    }
    rgb = oklchToRgb({ L, C: lo, h });
  }
  return rgbToHex(rgb.map(fromLinear));
}
```

Key facts:
- `built` (line 176-178) is `{ [rampName]: { [step]: hex } }` — only hex, the
  `{L, C, h}` values computed inside `buildRamp` are not retained after
  `toHex` converts them. This plan needs the `{L, C, h}` too, so `buildRamp`
  must be changed to also return them (see Step 2 — this is the one place a
  function's return shape changes, and it's internal to this script, not
  exported or imported elsewhere: `grep -rn "buildRamp\|from.*color-ramps"
  scripts/ src/` shows `color-ramps.mjs` is only ever run as
  `node scripts/color-ramps.mjs`, never imported).
- This script has **no existing dependency on an npm color library** —
  `rgbToOklch`/`oklchToRgb` (lines 70-92) are hand-written matrix math for
  the **sRGB** primaries specifically. Deriving the equivalent LMS→linear-P3
  matrix by hand for this plan would mean adding a second, unverified 3×3
  matrix with no way to catch a transposition or sign error except "the
  colors look subtly wrong" — exactly the kind of silent, hard-to-verify
  mistake this plan must not risk. Use `culori` (MIT-licensed, ~9KB, widely
  used, actively maintained) instead: it has correct, tested Display P3 and
  OKLCH conversions and gamut-mapping utilities (`converter`, `displayable`,
  `clampChroma`) built in. `culori` is not currently resolvable
  (`node --input-type=module -e "import('culori')"` fails with `Cannot find
  package 'culori'` — it is not even a transitive dependency today) —
  install it as a `devDependency` (this script only runs at build/dev time
  via `pnpm color-ramps`, never shipped to the browser).
- `pnpm-lock.yaml`/`package.json` currently list no `culori` anywhere.

### Step 2: retain `{L, C, h}` alongside hex in `buildRamp`

In `scripts/color-ramps.mjs`, `buildRamp`'s inner loop currently ends with
`ramp[step] = exact.hex ?? toHex(exact);` (for pinned steps) and
`ramp[step] = toHex({ L, C, h });` (for generated steps) — both discard
`{L, C, h}` after computing the hex. Change `buildRamp` to return, per step,
both the hex **and** the `{L, C, h}` it was derived from:

```js
function buildRamp({ pins, darkHue }) {
  // ...unchanged setup through the `last`/`lastIndex` computation...

  const ramp = {};
  const oklch = {}; // NEW: { [step]: {L, C, h} }
  STEPS.forEach((step, index) => {
    const exact = pinned.find((p) => p.index === index);
    if (exact) {
      ramp[step] = exact.hex ?? toHex(exact);
      oklch[step] = { L: exact.L, C: exact.C, h: exact.h };
      return;
    }
    let L, C, h;
    // ...unchanged L/C/h derivation for non-pinned steps...
    ramp[step] = toHex({ L, C, h });
    oklch[step] = { L, C, h };
  });
  return { ramp, oklch };
}
```

Update the one call site that consumes `buildRamp`'s return value:

```js
const built = Object.fromEntries(
  Object.entries(ramps).map(([name, def]) => [name, buildRamp(def)]),
);
```

`built[name]` is now `{ ramp, oklch }` instead of a flat hex map — update
every downstream reference (`json = { steps: STEPS, ramps: built }` becomes
`{ steps: STEPS, ramps: Object.fromEntries(Object.entries(built).map(([n, b]) => [n, b.ramp])) }`
so `palette.generated.json`'s shape is completely unchanged; the smoothness
report's `stepsOf`/`built[name]` references need the same `.ramp` accessor).

**Verify**: `pnpm color-ramps` runs without a `TypeError`; `git diff
src/styles/palette.generated.json` is empty.

### Step 3: P3 gamut mapping with `culori`

Add near the top of the script:

```js
import { clampChroma } from "culori";
```

Add a function that takes the same `{L, C, h}` shape already used elsewhere
and returns a P3-safe `oklch()` CSS string:

```js
/**
 * Maps an OKLCH color into the Display P3 gamut (wider than sRGB), reducing
 * chroma only as much as needed to fit P3 — unlike toHex()'s sRGB clip, most
 * gold/red steps need little or no reduction here. Formats as a CSS oklch()
 * string. Browsers without oklch() support simply ignore this declaration
 * and keep the sRGB hex declared just before it (see the output section).
 *
 * culori's `clampChroma(color, mode, rgbGamut)` finds the closest in-gamut
 * chroma at the same lightness/hue for the requested destination gamut, and
 * is a no-op (returns the color unchanged) when it's already in that gamut
 * — so a single call covers both the "fits already" and "needs reducing"
 * cases; no separate displayable()-style pre-check is needed. (culori's
 * displayable() always tests sRGB specifically — it has no gamut argument —
 * so it cannot be used to test P3 at all.)
 */
function toP3OklchString({ L, C, h }) {
  const color = { mode: "oklch", l: L, c: C, h: (h * 180) / Math.PI };
  const mapped = clampChroma(color, "oklch", "p3");
  const round = (n, d) => Math.round(n * 10 ** d) / 10 ** d;
  return `oklch(${round(mapped.l * 100, 2)}% ${round(mapped.c, 4)} ${round(mapped.h ?? 0, 2)})`;
}
```

(`culori`'s hue is in degrees; this script's internal `h` is radians — the
`(h * 180) / Math.PI` conversion matches that.)

**Verify**: run a one-off smoke test after wiring Step 4, e.g.
`node --input-type=module -e "import('./scripts/color-ramps.mjs')"` and
confirm it completes without error.

**Correction log (2026-09-30)**: the executor running this plan hit this

code above is corrected; if you're starting this plan fresh, ignore this log

### Step 4: emit both hex and `oklch()` per custom property

Change the output section from:

```js
const rampVars = Object.entries(built).flatMap(([name, ramp]) =>
  Object.entries(ramp).map(([step, hex]) => `  --${name}-${step}: ${hex};`),
);
```

to (using the `{ramp, oklch}` shape from Step 2):

```js
const rampVars = Object.entries(built).flatMap(([name, { ramp, oklch }]) =>
  Object.entries(ramp).flatMap(([step, hex]) => [
    `  --${name}-${step}: ${hex};`,
    `  --${name}-${step}: ${toP3OklchString(oklch[step])};`,
  ]),
);
```

Each custom property is declared twice in a row — hex first, then `oklch()`.
Per the CSS cascade, a browser that can't parse `oklch()` drops that
declaration and keeps the hex line; a browser that can, applies the later
(more specific-in-source-order) `oklch()` line. This is the entire mechanism
for the progressive enhancement — no `@supports` block needed.

**Verify**: `pnpm color-ramps` → `color-ramps: 6 ramps written.`; `head -6
src/styles/palette.css` shows a `--paper-50` line pair (hex then `oklch(...)`).
