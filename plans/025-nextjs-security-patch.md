## Why this matters

`pnpm audit` reports one critical advisory against this repo's pinned
`next` version:

```
GHSA-vcvr-r3jv-pc5j — "Next.js: Remote Code Execution in next/og
ImageResponse" — affects >=16.2.0 <16.3.6, patched in 16.3.6.
```

This repo pins `next` at exactly `16.3.5` (`package.json:24`), one patch
version behind the fix. The vulnerable surface is the Node.js
`ImageResponse` implementation in `next/og` when attacker-controlled values
reach SVG content/attributes/styles. `grep -rn "next/og\|ImageResponse" src`
returns no matches anywhere in this codebase, so the vulnerable API isn't
currently reachable — but it's a same-minor, same-major patch bump with no
announced breaking changes, so there's no reason to stay behind it. Patching
now also means this doesn't surface as an open finding in any future
dependency scan (CI security scanning, a hosting platform's audit, etc.).

## Scope

**In scope:**

- `package.json` — bump `next` and `eslint-config-next` to `16.3.6` (or the
  latest `16.3.x` patch available at execution time if a newer one has
  shipped — see Step 1).
- `pnpm-lock.yaml` — regenerated by `pnpm install`, not hand-edited.

**Out of scope — do not touch:**

- `react`/`react-dom` versions, or any other dependency — this is a
  single targeted security patch, not a broader dependency update pass.
- Any application code. Since `next/og`/`ImageResponse` are unused (verify
  this yourself in Step 1 before assuming it), there is no code to migrate.
- `next.config.ts` — no config changes are needed for this patch version.

## Steps

### Step 1 — Confirm the vulnerable API is unused, and find the target version

```bash
grep -rn "next/og\|ImageResponse" src --include="*.ts" --include="*.tsx"
```

Expect no matches. If this returns any matches, STOP and report instead of
proceeding — it would mean the vulnerable code path is actually reachable,
and whoever reviews this plan should know that changes the urgency framing
(still fix it, but the write-up needs to say "actively exploitable," not
"unreachable").

Then check what the latest `16.3.x` patch release actually is (newer than
`16.3.6` may exist by the time you execute this):

```bash
pnpm view next versions --json | grep -oE '"16\.3\.[0-9]+"' | tail -5
```

Use the highest `16.3.x` version from that list that is `>= 16.3.6`. Do not
jump to `16.4.x` or later — that would be a minor version upgrade, out of
scope for this patch-only plan.

### Step 2 — Bump the versions

In `package.json`:

- Change `"next": "16.3.5"` to `"next": "<target version>"` (the version
  found in Step 1).
- Change `"eslint-config-next": "16.3.5"` (in `devDependencies`) to the same
  target version, matching this repo's existing convention of keeping the
  two in sync.

**Verify:**

```bash
pnpm install
```

Expect exit 0. This regenerates `pnpm-lock.yaml` — do not hand-edit it.

### Step 3 — Confirm the advisory is resolved

```bash
pnpm audit
```

Expect `GHSA-vcvr-r3jv-pc5j` no longer appears in the output. If `pnpm
audit` reports a _different_ new advisory that wasn't there before (a
transitive dependency pulled in by the Next.js bump), STOP and report it
rather than deciding yourself whether it's acceptable to ship.

### Step 4 — Full verification pass

```bash
pnpm exec tsc --noEmit
pnpm lint
pnpm format:check
pnpm build
pnpm test
```

All must exit 0. This is the real regression check for a framework patch
bump — a patch version isn't supposed to change behavior, but this
confirms it for this specific app (build output, every route's a11y sweep,
every interaction test).

## Test plan

alter observable behavior.

## STOP conditions

- If `next/og` or `ImageResponse` turn out to be used anywhere (Step 1),
  stop and report — don't silently patch and move on when the risk framing
  the plan was written against turns out to be wrong.
- If `pnpm audit` surfaces a new advisory after the bump (Step 3), stop and
  report it with its severity and affected package — don't judge for
  yourself whether it's acceptable to ship.
- If `pnpm build` or `pnpm test` fail after the bump in a way that isn't
  obviously fixable by a one-line change clearly caused by this version
  bump (e.g. a config key Next.js renamed), stop and report the failure
  rather than making unrelated code changes to force it green — a "patch"
  release that breaks the build is itself worth flagging up, not silently
  worked around.
